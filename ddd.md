# Data Design Documentation (DDD)

## 1. Purpose and Scope

This document describes the current data architecture of the Alumni Tracking System, developed for a university Web Programming course.

The application currently uses ASP.NET Core MVC and Web API controllers with PostgreSQL persistence through Entity Framework Core (EF Core). This document distinguishes implemented features from proposed future improvements.

## 2. Current Architecture

The application uses the following data flow:

```text
Browser / API Client
        |
        v
ASP.NET Core Middleware Pipeline (Routing -> Authentication -> Authorization)
        |
        v
ASP.NET Core MVC / Web API Controllers
        |
        v
AlumniDbContext (Entity Framework Core)
        |
        v
Npgsql PostgreSQL Provider
        |
        v
PostgreSQL Database
```

MVC controllers return Razor Views for browser requests. API controllers expose HTTP endpoints and return API responses. Both access persistent data through the dependency-injected `AlumniDbContext`.

Cross-cutting HTTP pipeline components in `Program.cs`:
- `RequestLoggingMiddleware` logs completed MVC and Web API requests to the console.
- `ServerErrorGuardianMiddleware` catches unhandled exceptions and unstarted 5xx responses, logs them via `ILogger`, and returns safe JSON 500 payloads.
- `NotFoundGuardianMiddleware` returns structured JSON 404 responses for API / JSON requests, while non-API 404 responses re-execute `/Home/NotFound` (`Views/Shared/NotFound.cshtml`) via `UseStatusCodePagesWithReExecute`.
- `FileErrorLoggerProvider` persists error-level logs (`LogLevel >= Error`) to `logs/error.logs` alongside Console logging.
- `app.UseRouting()` -> `app.UseAuthentication()` -> `app.UseAuthorization()` evaluates the `Alumni.Auth` authentication cookie, populates `HttpContext.User`, and enforces `[Authorize]` / role-based policies before executing controller endpoints.

## 4. Database Context and Relationships

Source file: `Data/AlumniDbContext.cs`

The context exposes the following four entity sets:

- `Users` (`Users` table, with unique index on `Email`, required `PasswordHash`, and required `Role` defaulting to `"Alumni"`)
- `Announcements` (`Announcements` table)
- `JobPostings` (`job_postings` table, `1:N` with `Users` via `user_id`, `ON DELETE RESTRICT`)
- `Applications` (`applications` table, `M:N` join between `Users` and `JobPostings` with `UNIQUE (user_id, job_posting_id)` and `ON DELETE RESTRICT`)

EF Core maps these entities to PostgreSQL tables. The current model does not define a direct foreign-key relationship between users and announcements; announcement authorship is not represented by a `UserId` or author navigation property in the current entity model.

Extended academic profile entities such as departments, graduation records, and job experience tracking remain future domain enhancements and are not yet implemented in the database schema.

The database design specifications for `job_postings` and `applications` are documented in the sections below.

## Database Design: Job Postings Table (`job_postings`)

This section documents the database schema design and API specification for the `job_postings` table (implemented in `Models/JobPosting.cs`, `Data/AlumniDbContext.cs`, migration `20261021064649_AddJobPostings`, `JobPostingController`, and `ApiUserController`; optional domain rules not yet in the schema are explicitly noted below).

### 1. Table Definition

Table name: `job_postings`

Columns:

| Column Name | Data Type | Nullable | Key / Constraint | Description |
|---|---|---|---|---|
| `id` | `integer` | No (`NOT NULL`) | Primary Key | Unique identifier for each job posting |
| `user_id` | `integer` | No (`NOT NULL`) | Foreign Key (`users.id`) | References the user who created/owns the posting; required |
| `title` | `text` | No (`NOT NULL`) | None | Required text field specifying the job title |
| `company` | `text` | No (`NOT NULL`) | None | Required text field specifying the company name |

SQL Schema Definition:

```sql
CREATE TABLE job_postings (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id INT NOT NULL,
    title TEXT NOT NULL,
    company TEXT NOT NULL,
    CONSTRAINT fk_job_postings_users
        FOREIGN KEY (user_id)
        REFERENCES "Users" ("Id")
        ON DELETE RESTRICT
);
```

### 2. One-to-Many Relationship

The `job_postings` table establishes a one-to-many (1:N) relationship between users and job postings:
- **One user can create many job postings:** A single user can create and own multiple job postings.
- **Each job posting belongs to exactly one user:** Every job posting record is strictly associated with a single user owner.
- **Ownership identification:** The `user_id` column identifies the owner of the posting.

### 3. Foreign Key and Deletion Rule

- **Foreign Key:** `job_postings.user_id` references `users.id` (mapped to `"Users"("Id")` in PostgreSQL / EF Core).
- **Deletion Rule:** `RESTRICT` (or `NO ACTION`).
- **Explanation and Rationale:**
  - The deletion rule is configured as `RESTRICT` / `NO ACTION` so that a user with existing job postings cannot be deleted accidentally.
  - If a DELETE operation is executed against a record in `users` while that user still has one or more associated postings in `job_postings`, the database rejects the deletion and raises a foreign key violation error.
  - This rule is chosen over alternatives for critical data integrity reasons:
    - **Prevents accidental cascading data loss:** Unlike `CASCADE`, which would silently remove all job postings when a user is deleted, `RESTRICT` prevents accidental loss of job postings that may still be active or needed for historical tracking.
    - **Prevents orphaned records:** Unlike `SET NULL`, which is prohibited because `user_id` is a required (`NOT NULL`) field, `RESTRICT` ensures that every job posting always has a valid owner.
    - **Intentional account lifecycle:** To delete a user, an administrator or client must first explicitly reassign or delete their associated job postings, ensuring safe and deliberate data management.

### 4. API Endpoint: `POST /api/users/{id}/jobs`

The API provides an endpoint to create a job posting for a specified user:

- **HTTP Method and Route:** `POST /api/users/{id}/jobs`
- **Route Parameter:** `{id}` is the user ID from the URL, indicating the owner of the posting.
- **Request Body:** JSON payload containing `title` and `company`:
  ```json
  {
    "title": "Junior Developer",
    "company": "Acme"
  }
  ```
- **Ownership Determination:**
  - The server must determine ownership from the URL (`{id}`), not from a `user_id` supplied in the request body.
  - If a client supplies a `user_id` in the JSON request body, the server ignores or rejects it. The posting is always assigned the owner ID specified by `{id}` in the URL. This prevents clients from spoofing ownership or associating postings with unintended users.
- **Expected HTTP Responses:**
  - `404 Not Found`: If the user with ID `{id}` does not exist in the database. The server verifies that the user exists in `users` before creating the posting; if no matching user is found, it returns `404 Not Found`.
  - `201 Created`: If creation succeeds. The server persists the new record in `job_postings` and returns `201 Created` with the newly created posting, including its `id` and `user_id` in the response body.
  - `400 Bad Request`: If the request payload is malformed or missing required fields (`title`, `company`).

### 5. Example Request

`POST /api/users/1/jobs`

```json
{
  "title": "Junior Developer",
  "company": "Acme"
}
```

**Explanation:**
The resulting posting belongs to user `1` because the server extracts the owner ID directly from the URL route parameter (`{id} = 1`) rather than accepting a `user_id` from the request body.

**Example Response (`201 Created`):**

```json
{
  "id": 1,
  "user_id": 1,
  "title": "Junior Developer",
  "company": "Acme"
}
```

### 6. JobPosting Business Rules

The following domain rules define the field-level validation and optionality requirements for the `JobPosting` entity:

1. **`title`**
   - Required field.
   - Maximum length: 120 characters.
   - Must not be empty or `null`.

2. **`company`**
   - Required field.
   - Must not be empty or `null`.

3. **`city`**
   - Optional field.
   - Can be `null` or empty.

4. **`description`**
   - Optional field.
   - Can be `null` or empty.

> **Note:** In the current implementation (`Models/JobPosting.cs`, `Models/CreateJobPostingRequest.cs`, and the `job_postings` table), `title` and `company` are persisted as non-null `text` columns and validated for non-whitespace input in `POST /api/users/{id}/jobs`. The 120-character maximum length constraint for `title` and the optional `city` and `description` fields are documented here as domain rules and are not yet added to the active entity models, DTOs, or database schema.

## Database Design: Applications Table (`applications`)

This section documents the database schema design and API specification for the `applications` table, which serves as the join table implementing the many-to-many relationship between users (applicants) and job postings.

### 1. Table Definition

Table name: `applications`

Columns:

| Column Name | Data Type | Nullable | Key / Constraint | Description |
|---|---|---|---|---|
| `id` | `integer` | No (`NOT NULL`) | Primary Key | Unique identifier for each application record |
| `user_id` | `integer` | No (`NOT NULL`) | Foreign Key (`users.id`) | References the user who submitted the application; required |
| `job_posting_id` | `integer` | No (`NOT NULL`) | Foreign Key (`job_postings.id`) | References the job posting being applied for; required |
| `status` | `text` | No (`NOT NULL`) | None | Application status (e.g. `'applied'`, `'interview'`); required |

Unique Constraint:
- `UNIQUE (user_id, job_posting_id)`: A user cannot apply to the same job posting more than once. The database enforces this constraint, and duplicate submission attempts return HTTP `409 Conflict`.

SQL Schema Definition:

```sql
CREATE TABLE applications (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id INT NOT NULL,
    job_posting_id INT NOT NULL,
    status TEXT NOT NULL DEFAULT 'applied',
    CONSTRAINT fk_applications_users
        FOREIGN KEY (user_id)
        REFERENCES "Users" ("Id")
        ON DELETE RESTRICT,
    CONSTRAINT fk_applications_job_postings
        FOREIGN KEY (job_posting_id)
        REFERENCES job_postings (id)
        ON DELETE RESTRICT,
    CONSTRAINT uq_applications_user_job
        UNIQUE (user_id, job_posting_id)
);

CREATE INDEX idx_applications_user_id ON applications (user_id);
CREATE INDEX idx_applications_job_posting_id ON applications (job_posting_id);
```

### 2. Many-to-Many Relationship

The `applications` table acts as a join table linking `users` and `job_postings`:
- **Many users can apply to many job postings ($M:N$):** Multiple users can apply to the same job posting, and a single user can submit applications to multiple job postings.
- **One row per (user, posting):** Each application row represents a single application submitted by one user to one job posting.
- **Navigation Properties:**
  - `User.Applications` collection navigation property.
  - `JobPosting.Applications` collection navigation property.
  - `Application.User` and `Application.JobPosting` reference navigation properties.

### 3. Foreign Keys and Deletion Rule

- **Foreign Keys:**
  - `applications.user_id` references `users.id` (`"Users"("Id")`).
  - `applications.job_posting_id` references `job_postings.id`.
- **Deletion Rule:** `RESTRICT` (or `NO ACTION`).
- **Explanation:**
  - Both foreign keys use `RESTRICT` to prevent accidental deletion of user accounts or job postings that have active application history.
  - Deleting a user or job posting with associated applications is rejected by the database until those applications are explicitly handled.

### 4. API Endpoints

#### POST `/api/jobs/{id}/applications`
Submits an application to the specified job posting.
- **Route Parameter:** `{id}` is the job posting ID from the URL (`job_posting_id`).
- **Request Body:** JSON payload containing `user_id`:
  ```json
  {
    "user_id": 1
  }
  ```
- **Validation and Behavior:**
  - If the job posting with ID `{id}` does not exist: returns `404 Not Found`.
  - If the user with ID `user_id` does not exist: returns `404 Not Found`.
  - If the user has already applied to this job posting: returns `409 Conflict`.
  - If valid: persists the new application with `job_posting_id = {id}` and `status = 'applied'`, returning `201 Created` with the created application record.

#### GET `/api/jobs/{id}/applications`
Lists all applications submitted for a specific job posting.
- **Route Parameter:** `{id}` is the job posting ID.
- **Validation:** If the job posting with ID `{id}` does not exist, returns `404 Not Found`.
- **Response:** `200 OK` with an array of applications belonging exclusively to job posting `{id}`.

#### GET `/api/users/{id}/applications`
Lists all applications submitted by a specific user.
- **Route Parameter:** `{id}` is the user ID.
- **Validation:** If the user with ID `{id}` does not exist, returns `404 Not Found`.
- **Response:** `200 OK` with an array of applications belonging exclusively to user `{id}`.

### 5. Example Request

`POST /api/jobs/1/applications`

```json
{
  "user_id": 2
}
```

**Explanation:**
User `2` submits an application for job posting `1`. The server takes `job_posting_id = 1` from the URL route and `user_id = 2` from the payload.

**Example Response (`201 Created`):**

```json
{
  "id": 1,
  "userId": 2,
  "jobPostingId": 1,
  "status": "applied"
}
```

## Users and Their Roles

This section documents the users of the Alumni platform, their roles, operational responsibilities, data access permissions, and the implemented ASP.NET Core authentication and authorization architecture.

To maintain strict alignment with the repository source code, this section accurately describes what is **currently implemented** and explicitly separates **unfinished or planned future enhancements** (such as JWT Bearer API authentication and external university SSO).

### 1. User Types and Personas

The Alumni platform accommodates four user types interacting with academic records, communications, and career opportunities:

#### 1.1 Alumni / Graduate (`Alumni`)
- **Profile:** Verified graduates of the university across various faculties, degree programs, and graduation cohorts.
- **Role & Value in System:** Form the core community of the platform. Alumni share career opportunities with students and peers, establish professional networks, mentor current students, and maintain enduring ties with their alma mater.
- **Key Responsibilities:**
  - Maintain an up-to-date personal profile (`/Account/Profile`, `/Account/EditProfile`).
  - Publish employment and internship opportunities via `/JobPosting/MyJobPostings` (`POST /JobPosting/Create`).
  - Review candidate applications submitted to their own job postings (`/JobPosting/ApplicationsReceived`, `/JobPosting/Applications/{id}`).
  - Browse public announcements (`/Announcement`), the alumni directory (`/User`), and job opportunities (`/JobPosting`).

#### 1.2 Student (`Student`)
- **Profile:** Currently enrolled undergraduate or graduate students at the university.
- **Role & Value in System:** Emerging talent seeking career entry points, mentorship, internships, and networking opportunities with established graduates.
- **Key Responsibilities:**
  - Discover and explore the public alumni directory (`/User`, `/User/Details/{id}`).
  - Browse verified job openings (`/JobPosting`, `/JobPosting/Details/{id}`) and submit applications (`POST /JobPosting/Apply/{id}`).
  - Track personal application history and statuses (`/JobPosting/MyApplications`, `/Account/Profile`).
  - Follow official university announcements (`/Announcement`) and maintain their own profile (`/Account/EditProfile`).

#### 1.3 Administrator (`Administrator`)
- **Profile:** University alumni relations officers, departmental administrators, and authorized institutional platform managers.
- **Role & Value in System:** Safeguard platform integrity, govern user accounts and roles, publish official university communications, and enforce institutional governance standards.
- **Key Responsibilities:**
  - Monitor platform metrics and recent registrations via the Admin Dashboard (`/Admin`).
  - Manage user accounts and roles (Create, Read, Details, Update, Password Reset, Delete) via `/Admin/Users` (`AdminController`) and `/User` write actions (`UserController`).
  - Draft, publish, edit, and delete official institutional announcements and bilingual bulletins (`/AnnouncementAdmin`).
  - Maintain their own administrator profile (`/Account/Profile`, `/Account/EditProfile`) while protected against accidental self-demotion or self-deletion.

#### 1.4 Guest / Public Visitor (`Guest` / Unauthenticated)
- **Profile:** Prospective students, external employers, family members, academic researchers, and the general public.
- **Role & Value in System:** Explore the university's alumni community and read publicly accessible announcements without requiring an active account.
- **Key Responsibilities:**
  - Freely browse the public homepage (`/`), about page (`/about`), public announcements (`/Announcement`), alumni directory (`/User`), and public job listings (`/JobPosting`).
  - Register a new `Student` or `Alumni` account (`/Account/Register`) or sign in to an existing account (`/Account/Login`).

### 4. Relationship Between Users and Main System Features

```text
+-----------------------------------------------------------------------------------+
|                                  USER ("Users")                                   |
|                    Id | Name | Email (UNIQUE) | PasswordHash | Role               |
```

#### 4.1 Alumni Directory, User Management, and Profile Governance
- The `"Users"` table (`Models/User.cs`) persists `Id`, `Name`, `Email` (enforced unique via `IX_Users_Email`), `PasswordHash`, and `Role` (`"Student"`, `"Alumni"`, or `"Administrator"`).
- Public directory reads are served by `UserController` (`/User`, `/users`, `/User/Details/{id}`), while all write actions in `UserController` require `[Authorize(Roles = "Administrator")]`.
- Full administrative user governance (search, role filter, create, details, edit, optional password reset, delete with safety guards) is centralized in `AdminController` (`/Admin`, `/Admin/Users`).
- Authenticated users manage their own identity exclusively via `AccountController.Profile` (`/Account/Profile`) and `AccountController.EditProfile` (`/Account/EditProfile`).

#### 4.2 Official Announcements vs. Public Bulletins
- The `"Announcements"` table (`Models/Announcement.cs`) stores institutional communiqués with bilingual support (`Title`, `Content`, `TitleEn`, `ContentEn`, `CreatedDate`).
- **Authorship Decoupling:** The `"Announcements"` table does not contain a `user_id` foreign key; announcements represent institutional statements rather than personal posts.
- Public visitors, students, and alumni have read-only access via `AnnouncementController` (`/Announcement`, `/Announcement/Details/{id}`).
- Administrators exclusively manage announcements via `AnnouncementAdminController` (`/AnnouncementAdmin`), protected by `[Authorize(Roles = "Administrator")]`.

#### 4.3 Career Opportunities and Job Postings (1:N Relationship)
- The `job_postings` table maintains a one-to-many ($1:N$) relationship with `"Users"` via `user_id -> "Users"("Id")` with `ON DELETE RESTRICT`.
- **Ownership Model:** Each posting is associated with `JobPosting.UserId`. In MVC, authenticated `Alumni` users view and publish their own postings via `/JobPosting/MyJobPostings` and `POST /JobPosting/Create` (`UserId` is extracted strictly from `ClaimTypes.NameIdentifier`).
- Public job browsing (`/JobPosting`, `/JobPosting/Details/{id}`) remains accessible to all visitors.

#### 4.4 Job Applications ($M:N$ Relationship and Candidate Privacy)
- The `applications` table implements the many-to-many ($M:N$) join between applicants (`user_id`) and postings (`job_posting_id`) with `UNIQUE (user_id, job_posting_id)` and `ON DELETE RESTRICT` on both foreign keys.
- **Role-Separated Views:**
  - **Student Applicant View:** `/JobPosting/MyApplications` (`[Authorize(Roles = "Student")]`) displays only applications where `a.UserId == currentUserId`.
  - **Hiring Alumnus View:** `/JobPosting/ApplicationsReceived` (`[Authorize(Roles = "Alumni")]`) displays only applications where `a.JobPosting.UserId == currentUserId`.
  - **Per-Job Registry Privacy (`/JobPosting/Applications/{id}`):** Shows the full candidate list only to the posting's `Alumni` owner or an `Administrator`. Other authenticated users see only their own application record, and unauthenticated visitors see no candidate personal data.

### 5. Distinction Between Regular Users and Administrative Users

The architecture enforces a clear separation between **Regular Users** (`Alumni`, `Student`, `Guest`) and **Administrative Users** (`Administrator`):

| Governance Dimension | Regular Users (`Alumni`, `Student`, `Guest`) | Administrative Users (`Administrator`) |
|---|---|---|
| **Resource Scope** | **Self-Centric / Resource Ownership:** Authenticated regular users access public pages and only their own profile (`/Account/Profile`), own applications (`/JobPosting/MyApplications`), or own job postings and received candidates (`/JobPosting/MyJobPostings`, `/JobPosting/ApplicationsReceived`). | **System-Wide / Institutional Scope:** Administrators view platform-wide metrics (`/Admin`), manage all user accounts and roles (`/Admin/Users`), view full applicant lists on `/JobPosting/Applications/{id}`, and publish official announcements (`/AnnouncementAdmin`). |
| **Institutional Voice** | **Zero Publishing Authority for Announcements:** Blocked from `/AnnouncementAdmin` with redirect to `/Account/AccessDenied`. | **Exclusive Editorial Control:** Full CRUD access to `/AnnouncementAdmin` via `[Authorize(Roles = "Administrator")]`. |
| **Directory Governance** | **Self-Profile Only:** Can update only their own `Name` and `Email` via `/Account/EditProfile`; cannot change roles or edit other users (`/User/Edit/{id}` blocked). | **Full Directory Authority:** Can create users with any role, edit details/roles, reset passwords, and delete eligible accounts; protected by self-demotion, self-deletion, and dependency guards. |
| **Role Escalation Controls** | Cannot self-register as `Administrator` (`/Account/Register` rejects `"Administrator"`); `EditProfileViewModel` applies `[BindNever]` to `UserId` and `Role`. | Assigned strictly via server configuration (`Admin:Email` / `ADMIN_EMAIL`) or by an existing administrator through `/Admin/Users`. |

### 6. Implemented ASP.NET Core Authentication and Authorization Architecture

This section documents the active authentication and authorization implementation in the codebase.

#### 6.1 Cookie Authentication Configuration & Middleware Pipeline (`Program.cs`)
In `Program.cs`, authentication and password hashing services are registered in the DI container:
- `builder.Services.AddScoped<IPasswordHasher<User>, PasswordHasher<User>>();`
- `builder.Services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme).AddCookie(...)`:
  - `LoginPath = "/Account/Login"`
  - `LogoutPath = "/Account/Logout"`
  - `AccessDeniedPath = "/Account/AccessDenied"`
  - `Cookie.Name = "Alumni.Auth"`
  - `Cookie.HttpOnly = true`
  - `Cookie.SameSite = SameSiteMode.Lax`
  - `Cookie.SecurePolicy = CookieSecurePolicy.SameAsRequest`
  - `ExpireTimeSpan = TimeSpan.FromDays(7)` with `SlidingExpiration = true`

Middleware execution order in `Program.cs`:
```csharp
app.UseRouting();

app.UseAuthentication(); // Validates Alumni.Auth cookie and populates HttpContext.User
app.UseAuthorization();  // Enforces [Authorize] and role requirements

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.MapControllers();
```

#### 6.2 Identity, Claims, and Password Hashing (`AccountController.cs`)
Passwords are never stored or compared in plain text. `IPasswordHasher<User>` (`PasswordHasher<User>`) generates cryptographically salted PBKDF2-SHA256 hashes on registration (`AccountController.Register`) and admin user creation/password reset (`AdminController.CreateUser`, `EditUser`), and verifies passwords during sign-in (`AccountController.Login`).

Upon successful authentication (and upon updating profile details in `AccountController.EditProfile`), `HttpContext.SignInAsync` issues a `ClaimsPrincipal` under `CookieAuthenticationDefaults.AuthenticationScheme`:
```csharp
var claims = new List<Claim>
{
    new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
    new Claim(ClaimTypes.Name, user.Name),
    new Claim(ClaimTypes.Email, user.Email),
    new Claim(ClaimTypes.Role, user.Role) // "Administrator" | "Alumni" | "Student"
};
var claimsIdentity = new ClaimsIdentity(claims, CookieAuthenticationDefaults.AuthenticationScheme);
var claimsPrincipal = new ClaimsPrincipal(claimsIdentity);
```

Implemented account lifecycle flows in `AccountController`:
- **Registration (`GET/POST /Account/Register`, `/register`):** Validates `RegisterViewModel` with `[ValidateAntiForgeryToken]`, rejects `"Administrator"` and unknown roles, checks case-insensitive duplicate emails, hashes the password, persists the `User`, and redirects to Login with a confirmation message.
- **Login (`GET/POST /Account/Login`, `/login`):** Validates `LoginViewModel` with `[ValidateAntiForgeryToken]`, performs case-insensitive email lookup, verifies `PasswordHash`, returns a generic error message (`"Invalid email address or password."`) on failure to prevent user enumeration, promotes configured admin emails if matched, issues the `Alumni.Auth` cookie (persistent for 7 days if `RememberMe` is checked), and redirects safely via `Url.IsLocalUrl(returnUrl)`.
- **Logout (`POST /Account/Logout`, `/logout`):** Protected by `[ValidateAntiForgeryToken]`, calls `HttpContext.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme)` to clear the cookie, and redirects to `/`. Direct `GET /Account/Logout` requests redirect safely to `/`.
- **Profile & Edit Profile (`GET /Account/Profile`, `GET/POST /Account/EditProfile`):** Protected by `[Authorize]`. Both actions take no `id` route parameter and resolve the user solely from `ClaimTypes.NameIdentifier`. `EditProfile` uses `EditProfileViewModel` (`[BindNever]` on `UserId` and `Role`, no `PasswordHash` field), enforces `[ValidateAntiForgeryToken]` and case-insensitive duplicate email checks, updates only `Name` and `Email`, and refreshes the authentication cookie so updated claims take effect immediately.
- **Access Denied (`GET /Account/AccessDenied`, `/access-denied`):** Renders `Views/Account/AccessDenied.cshtml` when an authenticated user attempts to access a route requiring a different role.

#### 6.3 Role-Based Authorization & Data Ownership Guards
Authorization is enforced server-side across controllers:
1. **Declarative `[Authorize]` & `[Authorize(Roles = "...")]` Attributes:**
   - `AdminController` (`/Admin`, `/Admin/Users`, Create/Details/Edit/Delete): `[Authorize(Roles = "Administrator")]`.
   - `AnnouncementAdminController` (`/AnnouncementAdmin`): `[Authorize(Roles = "Administrator")]`.
   - `UserController` write actions (`CreateFromUsersRoute`, `Create`, `Edit`, `Delete`, `DeleteConfirmed`): `[Authorize(Roles = "Administrator")]`.
   - `JobPostingController.MyApplications` (`/JobPosting/MyApplications`): `[Authorize(Roles = "Student")]`.
   - `JobPostingController.MyJobPostings`, `Create`, `ApplicationsReceived`: `[Authorize(Roles = "Alumni")]`.
   - `AccountController.Profile`, `EditProfile`: `[Authorize]`.
2. **Ownership & Safety Guards (Controller-Level):**
   - `AdminController` blocks an administrator from revoking their own `Administrator` role (`EditUser`), blocks self-deletion (`DeleteUserConfirmed`), and checks dependent `JobPostings` / `Applications` before deletion to respect `ON DELETE RESTRICT`.
   - `JobPostingController` filters `MyApplications` by `a.UserId == currentUserId`, `MyJobPostings` by `j.UserId == currentUserId`, `ApplicationsReceived` by `a.JobPosting.UserId == currentUserId`, and `/JobPosting/Applications/{id}` by owner/admin visibility.
   - `JobPostingController.Apply`, `ApiJobController.CreateApplicationForJob`, and `ApiApplicationController.CreateApplication` verify `User?.Identity?.IsAuthenticated == true`, extract `ClaimTypes.NameIdentifier`, and return `401 Unauthorized` (unauthenticated) or `403 Forbidden` (client-supplied `user_id` mismatch).
   - *Note:* Formal ASP.NET Core `AuthorizationHandler<IAuthorizationRequirement>` policy classes are not currently implemented; resource ownership is enforced directly in controller actions and queries.

#### 6.4 Dynamic Role-Based Navigation (`Views/Shared/_Layout.cshtml`)
The shared navigation bar dynamically detects authentication state and role using `User.Identity.IsAuthenticated` and `User.IsInRole(...)` (never hardcoding emails), displaying active-page highlighting, Bootstrap icons, user name + role pill badge, and `TR | EN` bilingual labels:
- **Guest (Not Logged In):** `Home` (`/`), `Announcements` (`/Announcement`), `Alumni` (`/User`), plus `Login` (`/Account/Login`) and `Register` (`/Account/Register`).
- **Student:** `Home`, `Announcements`, `Alumni`, `Job Opportunities` (`/JobPosting`), `My Applications` (`/JobPosting/MyApplications`), `My Profile` (`/Account/Profile`), plus `Logout` (`POST /Account/Logout`).
- **Alumni:** `Home`, `Announcements`, `Alumni`, `Job Opportunities`, `My Job Postings` (`/JobPosting/MyJobPostings`), `Applications Received` (`/JobPosting/ApplicationsReceived`), `My Profile`, plus `Logout`.
- **Administrator:** `Home`, `Admin Dashboard` (`/Admin`), `User Management` (`/Admin/Users`), `Announcement Management` (`/AnnouncementAdmin`), `My Profile`, plus `Logout`.

#### 6.5 Authentication Database Migration & Admin Seeding
- **Migration:** `Migrations/20261125064343_AddUserAuthenticationAndRoles.cs` adds `PasswordHash` (`text`, `NOT NULL`, default `""`), `Role` (`text`, `NOT NULL`, default `"Alumni"`), and the unique index `IX_Users_Email` on `"Users"("Email")`. Valid role strings (`Administrator`, `Alumni`, `Student`) are enforced in application controllers (`AccountController`, `AdminController`).
- **Seeding & Configuration-Based Admin Promotion:**
  - `Data/Factories/UserFactory.cs` generates initial seed users (`Administrator`, `Alumni`, and `Student` accounts) with hashed passwords via `PasswordHasher<User>`.
  - `Data/Seeders/DatabaseSeeder.cs` seeds initial records when `"Users"` is empty and reads the configured administrator email from `Admin:Email` (`appsettings.json`) or the `ADMIN_EMAIL` environment variable. If a user with that email already exists, `DatabaseSeeder` (on startup) and `AccountController.Login` (on sign-in) promote the existing account to `"Administrator"` without creating duplicate records.
- **Not Yet Implemented (Future Evolution):** JWT Bearer authentication for REST APIs, ASP.NET Core Identity tables (`IdentityDbContext`), and external University Single Sign-On (OpenID Connect / SAML 2.0) are not implemented in the current codebase.

## 8. Persistence and Forgetting Test

A database persistence test was performed during development:

1. Create a test record in PostgreSQL.
2. Stop the Compose services using `docker compose down`.
3. Recreate the services using `docker compose up -d`.
4. Query the record again.
5. Verify that the record still exists.

The test record remained available after container recreation. This demonstrates that the PostgreSQL named volume preserves database files independently of the container lifecycle.

Important: `docker compose down` does not normally remove named volumes. Avoid `docker compose down -v` unless you intentionally want to remove the volume and its stored database data.

The manually created `forgetting_test` table was used for this persistence test; it is not one of the application's EF Core entity sets.

## 10. Current Limitations and Future Work

The following items are **not** yet implemented in the current codebase and remain planned for future development phases:

- **JWT Bearer Authentication & REST API RBAC:** REST API endpoints in `ApiUserController`, `GET` endpoints in `ApiJobController` / `ApiApplicationController`, and `POST /api/users/{id}/jobs` do not yet enforce JWT Bearer authentication or role-based `[Authorize]` attributes (only `POST` application creation endpoints currently verify authenticated cookie sessions).
- **External University SSO & ASP.NET Core Identity Tables:** External Single Sign-On (OpenID Connect / SAML 2.0) and full `IdentityDbContext` table integration are not implemented.
- **Self-Service Password Management & Email Verification:** Users cannot yet change their own password from `/Account/Profile`, reset forgotten passwords via email, or verify email addresses during registration.
- **Job Posting Edit/Delete & Admin Job Moderation:** Alumni and Administrators cannot yet edit or delete published job postings through MVC views, and there is no dedicated Admin Job Management panel.
- **Extended Academic & Career Profile Fields:** Department, graduation year, biography, profile photo, `CreatedAt` registration timestamp, and job experience tracking are not yet in `Models/User.cs` or the database schema.
- **Additional Schema & Business Constraints:** Foreign-key authorship between `Users` and `Announcements`, a database-level PostgreSQL `CHECK` constraint on `"Users"."Role"`, and optional `JobPosting` fields (`city`, `description`, and 120-character `title` length limit) are not yet added to the active schema.
